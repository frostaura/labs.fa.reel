# Live decisions

## Founder — programme and honesty (2026-09-09)

- **Programme: both, model first.** *Why:* the ledger (12/12 non-positive, −80%), the served-title correlation (−0.004) and the retro loop (5.78 vs 6.74) together say the FastTree engine has no measurable edge. Dean chose to repair the serving arithmetic and the evaluation instrument **before** any user-facing number changed, then run the product programme (closed loop, supply, taste profile, lens copy). The M2 gate is treated as a **consistent negative, not instrument noise** — repairing the instrument tells us where and how much, not whether.
- **Honest from day one.** *Why:* publish the real track record and the "what might bug you" caution immediately, framed as "here is how wrong I am and what I am doing about it". A calibrated number that is honest but *constant* is explicitly not acceptable — hence the calibrator collapse guard in `gotchas.md`.
- **Filters: a cost meter, and Dean decides in-app.** *Why:* the plan must never change a content rule on his behalf. Discovery became filter-aware and the conditions editor shows the marginal cost of each rule; no rule is changed automatically.
- **Do not normalise the residual bias away without a replacement calibrator.** *Why:* the −1.68 offset was compensating a base model that over-predicts by 1–2.7 points. Removing it alone makes every displayed number jump and get *less* honest. It was replaced by an explicit monotone calibrator applied last; the head is kept only for discriminative corrections.
- **Exposure logging is append-only per serve, with a derived rollup and a temporal join as the primary attribution.** *Why:* only ~2% of ratings are made in-app, and the adversarial wave showed a de-duplicated-on-build design loses exactly the drift the founder complains about and never sees the live refill path. Written where cards are served, including the refill; no client viewport beacon; the 7-snapshot prune stays.
- **No hero exploration slot.** *Why:* with ~421 eligible titles ranked end to end there is nothing to explore. Supply and filters are the levers.

## Security

- **The npm audit gate allows narrow, EXPIRING waivers, and one is active (2026-08-07).** `src/frontend/scripts/audit-gate.mjs` (`npm run audit:gate`) is `npm audit --audit-level=high` plus named waivers carrying a reason and a review date, and it **fails** once that date passes. It exists because react-router has no clean version — GHSA-wrjc-x8rr-h8h6 covers 6.0.0–7.17.0 and GHSA-qwww-vcr4-c8h2 covers 7.12.0–8.2.0 with no 8.x published. Reel is a client-only SPA with no RSC entry point, so the RSC-mode CSRF path is unreachable while the open redirect is not; **7.18.2 is the better posture, not the more convenient one**, and GHSA-qwww-vcr4-c8h2 is waived until **2026-11-07**. Verified non-vacuous against an un-waived high and an expired waiver. **Waiving an advisory is a cybersecurity decision, which root `CLAUDE.md` places at parent level — this one needs founder review at expiry, never a silent renewal.**
- **Vulnerable transitives get an explicit pin, not a suppression.** `Microsoft.OpenApi` 2.7.5 and `System.Security.Cryptography.Xml` 10.0.10, both commented to be removed once upstream ships a patched transitive. The `security` CI job fails the build otherwise.

## Product remediation (2026-08-10) — each with its why

- **Trakt history writeback is movie-only** (`4095762`). *Why:* a bare show object on Trakt `sync/history` marks every aired episode watched — rating a show wrote ~801 fake plays into the founder's real history. Shows sync ratings only; `RemoveFromHistory` (anchored on `WatchedTitle.ReelLoggedWatchedAt`) makes the movie path reversible.
- **Stable-tonight contract** (`0db6625`). *Why:* two contradictory complaints ("rows never change" / "hero churned 3×/hour") resolve as: identical within a UTC day (Preserve mode + no-op snapshot suppression), guaranteed different across days (day-seeded AnchorRotation), immediate on user action. Do not re-tune one side without re-checking the other.
- **Negations quarantine, never mix** (`79d8c60`, `06016fc`). *Why:* the reserve top-up used to refill unflagged, so "no horror" showed 7 horror cards whose captions admitted the violation. Contradicting titles now appear only under a labelled "Outside your request" channel, and genre exclusions match Subgenres/Keywords because TMDB's TV taxonomy has no horror genre.
- **Dislike reasons demote by similarity, not just exclusion** (`0d207cf`). *Why:* reactions previously hid one title only. Reason-weighted demotion (capped 1.5 points, 180-day decay) applies at every scoring surface; FeatureSchema v3's bump deliberately forces a per-account retrain on deploy.
- **Why-lines are anchored, specific and never self-defeating** (`94f9a8d`, `7232884`); **PIN unlock is a DataProtection token, never the cached raw PIN** (`991e013`); **lookup ≠ suggestion extends to TMDB** (`d3ea403` — global TMDB rows plus on-demand hydration keep the zero-footprint invariant while making all of TMDB addressable); **digest/push/blend ship behind existing patterns** (`c5483f5` — self-generated VAPID, exclusion-only blend intersection).

## Engineering calls (2026-09-10)

- **Every number the backend formats is INVARIANT, and a source-level guard enforces it.** *Why:* nothing here is localised — prompts, TMDB/Trakt query strings, cache keys, stored `ContentFilter.Value` rows, SSE payloads and job messages are machine-read or compared as exact strings, so a comma decimal separator is a wrong answer, not a rendering choice, and TMDB *ignores* a malformed parameter rather than rejecting it. Three defences, all load-bearing: the `Program.cs` culture pin, `string.Create(CultureInfo.InvariantCulture, …)` at each site, and `CultureSensitiveFormattingGuardTests` grepping for shapes **CA1305 cannot see**. **`Convert.ToDecimal`/`ToInt32` in `EligibilityQueryBuilder` stay provider-less on purpose** — EF translates only the single-argument overloads, and a provider makes the predicate untranslatable (~40 integration tests go red).
- **"It only fails locally" is a hypothesis, not a diagnosis.** *Why:* every `[LocalFlakyFact]` row ever quarantined turned out to be a real defect — a fake TMDB client returning a null language, and a test asserting a contract deliberately deleted in `2767cf9`. The pin and the attribute stay so that adding a row remains a deliberate decision.
- **`PersonAffinities` has a writer, and it forks no maths** (`PersonAffinityWriter`). *Why:* the entity, index, tenancy filter and a reader all shipped with no writer, so discovery arm 2 contributed nothing to any feed build — silently. Affinity and pool size come from `VerifiedPeople`, the same path the why-sentences read, so a stored row cannot quote a different number than the card. The pool is **role-agnostic**. `FeatureVectorBuilder` still recomputes as-of the split point and must never read this table — that is the leakage guarantee.
- **Iteration 17 (FeatureSchema v6) has a PRE-REGISTERED ledger rule, written before the iteration ran.** v6 ships if the mean relative NDCG lift across the five origins improves over iteration 16 **and** `NdcgLiftCiLow` does not move further negative; otherwise the bump is **reverted**. "No lift, CI unchanged" is a **revert**, not a keep. *Why:* iterations 13–16 have each been read after the fact, and a bump that costs every account a retrain needs a stopping rule that cannot be renegotiated once the number is on screen. `INTERLEAVE_ENABLED` must stay off across the comparison — a pool change mid-mSPRT silently invalidates it.
  - **Outcome, 2026-09-11: REVERTED per the rule.** Iteration 17 (v6) measured NDCG@10 **0.053** vs popularity 0.198, CI **[−0.356, +0.026]**, Spearman 0.116, holdout 209; the latest iteration 16 (v5) measured **0.056** vs the same 0.198, CI [−0.43, +0.08]. No lift, CI not improved → the bump came out of `main`, unrenegotiated. **The instrument is noise-dominated:** two v5 runs over identical data returned **0.000 and 0.056**, a spread wider than the effect being looked for, so this reads as "unmeasurable at a 209-row holdout", **not** "the watched-history features carry no signal". The four v6 entries below are kept as the record of what was built and why — **none of that code is in `main`**; `FeatureSchema.Version` is back to 5 and **6 is a burned number, so the next bump is 7**. Re-proposing whole-history features is legitimate; re-proposing them against this holdout is not.
- **Schema v6 = 137 features (five appended scalars), and the plan's "138" was never reachable.** The five: `simWatchedCentroid` + `hasWatchedCentroid` (cosine to the centroid of titles WATCHED but not RATED as-of), `simRewatchCentroid` + `hasRewatchCentroid` (`min(plays,3)`-weighted centroid of `Plays >= 2` titles, rated or not), `watchedGenreShare` (share of the watched-unrated pool sharing ≥1 genre with the candidate, candidate excluded from both halves when it is a member). *Why the bump at all:* every user-side feature before v6 read RATED titles only — 2,045 of the founder's 3,354 watched titles — so 1,363 titles he chose and finished, and 608 he watched more than once, fed nothing. *Why 137:* 132 + 5. The plan said "132 → 138" and scoped seven features; 132 + 7 is 139, so the written width was wrong either way. Fourth time a hand-typed width has been wrong in this project's prose — nothing interpolates a literal, and `FeatureSchema.VectorLength` is the only answer.
- **The v6 kNN pair was built, measured and dropped on a pre-registered cost gate — not on taste.** `nearestRatedNeighbourRating` / `nearestRatedNeighbourSim` (k = 3 distance-weighted over the account's own rated titles, self-excluded by id, pruned by the two nearest taste clusters recomputed as-of) were written in full and then removed. *Why:* a full `EvalHarness` run over a copy of the live database, warm — **2.8–2.9 s at v5**, **3.8–4.2 s with the five scalars that shipped** (1.3–1.5×), **12.6–12.8 s with the kNN pair added** (4.4–5.5× depending on machine load) — against a stated 2× ceiling. The cost is not the scan: building the search index (every rated embedding L2-normalised, plus a k-means pass) alone took `BuildTasteStateAsync` from ~100 ms to ~1,036 ms, and the harness pays that five times per run. Cluster pruning bought ~4×, which is real and not enough. The claim they carried is unresolved and worth revisiting behind a **materialised, incrementally-maintained** neighbour index, on its own bump with its own measurement — never by re-adding them to the per-build recompute.
- **Leave-one-out for the v6 pools, and where it actually fires.** Both centroids subtract a member's own contribution before the pool describes it — the unweighted `(mean·n − own)/(n − 1)` for the watched pool, the weighted `(mean·W − wᵢ·own)/(W − wᵢ)` for the rewatch pool, which is why `SelfExclusion` carries per-title rewatch weights and not just their total. *Why it matters where:* the REWATCH pool takes rated titles, so a training row is routinely a member and that is the live subtraction. The WATCHED-UNRATED pool excludes rated-as-of titles by construction and `EvalHarness`'s holdout is triple-filtered to titles unwatched at the split, so neither half of the harness can be a member — the subtraction is kept because the title-detail path scores watched-and-unrated titles directly. Stating that honestly is the point: a guard claimed to protect something it structurally cannot is how a guard becomes decoration.
- **"Watched as of X" is `LastWatchedAt <= X`, everywhere.** *Why:* `FirstSyncedAt` is immutable but it is the INGEST date — ~3,354 of the founder's watched rows share one bulk-link timestamp, so an as-of filter on it is all-or-nothing at the day Trakt was linked, which is the collapse `UserRating.FirstRatedAt` exists to avoid. `LastWatchedAt` is mutable and that mutability cannot leak: it only moves FORWARD, and a forward move can only push a title OUT of an as-of pool, never admit one that had not been watched by then. `TasteClusterProvider` already made this call; two definitions of "watched" in one codebase is the drift this repo keeps paying for. A null `LastWatchedAt` reads as not-yet-watched. And "unrated" is taken as the exact complement of the rated set the taste state already built, from that set rather than a second query, so the two pools cannot drift into overlapping.
- **One score resolution across `FeedItem`, `TitleScore` and the exposure log (2 dp).** *Why:* a calibration join inherits the coarsest side, and `FeedItem`'s 1 dp put a 0.05 quantisation floor under residuals of the same order as the deltas being measured.

## Engineering calls (2026-09-10/11)

- **Cross-reference verdicts NUDGE UP on Keep only — nothing is demoted, the hero is never barred, and nothing may enter `EligibilityQueryBuilder` from a model.** *Why (measured 2026-09-11 on the founder's own holdout, five origins pooled):* prompt v2 keeps later averaged 6.83 against 6.16 for outs, were loved 33% and disliked 8% of the time against base rates of 23% / 15%, AUC 0.655 — real signal in KEEP; but its outs still caught 16.2% [12.3, 21.0] of titles he went on to love (v1: 9.1% vs a true-rule-out of 11.5%, AUC 0.611 — no discrimination), so OUT has not earned a demotion. Keep factor `1 + 0.2×conf`, bounded so a keep never outweighs a full rating point of model opinion. *Why:* that file encodes founder-locked USER statements (watched, rated, reacted); an LLM opinion there would be load-bearing on a locked rule and a false rule-out would be permanently unobservable — the closed loop needs the ruled-out arm served sometimes. PR4 (round 2, round-3 slice replacement, any demotion) stays gated on a prompt whose OUT arm clears Wilson-upper ≤ 15% false-rule-out.
- **`Round` is in the verdict key and the model artifact is not.** *Why:* without the round, round 2 overwrites round 1 and "two keeps" has nothing to count; with the artifact in the key the whole verdict cache goes cold every retrain night (`TasteProfileHash` already made this call for lens copy). A `ProfileHash` move demotes verdicts to stale at half strength rather than invalidating them, so a hash step costs a drain, not a re-judgement.
- **The `rerank` purpose finally has a ceiling, split four ways, with background builds stopping at 70%.** *Why:* it was the only LLM spend with no cap; a single family ceiling that a feed build could exhaust would starve the founder's own chat and look intentional.
- **Two rows of tonight's picks are one column-major CSS grid with `HeroSize` untouched; multi-centroid retrieval keeps the drift arm and floors every cluster at 25 pulls.** *Why:* one scroll container shares `scrollLeft` by construction and column-major keeps DOM order = rank order; `HeroSize` also sets `FloorRelaxMinimum`, so the second row pages from `/feed/more`. The per-cluster floor is what stops a dominant cluster reproducing single-centroid behaviour at extra cost; the drift arm is the only signal faster than the 365-day half-life; the paginator takes three clusters because a home load fires every rail.
- **`hnsw.iterative_scan = 'strict_order'` on every connection, wired from `ReelDbContext.OnConfiguring` rather than from DI.** *Why:* the flaw belongs to every filtered vector query in the codebase, not to one arm, so a per-call-site `SET LOCAL` would need its own transaction and would be forgotten by the next arm added. Wiring it in `OnConfiguring` means a context built by hand — which is exactly what the integration fixture does — cannot end up with a different retrieval contract from production, so the suite is actually guarding the thing that ships. `strict_order` over `relaxed_order` because both call sites treat the result as distance-ordered; cheapening the ordering would trade one silent wrongness for another. The statement is swallowed on failure: a retrieval setting must never be why a connection cannot open.
- **Test isolation for embeddings is a shared base class, not a fourth per-fixture patch.** *Why:* three fixtures had each independently diagnosed and fixed their own half of the contamination — row deletion, reserved dimensions, a non-English language — and the victim broke again as soon as a fourth embedded fixture landed. Per-fixture care does not compose over a shared index. `EmbeddedCatalogTestBase` removes what each test added (snapshot on init, difference on dispose — never a truncate, so a class cannot destroy rows another class still needs), and a source guard fails the build on a class that seeds `TitleEmbeddings` without it.
- **`CrossReferenceBacktestTests` seeds per test instead of caching a static account.** *Why:* per-test embedding cleanup and a class-lifetime seed cannot both be true, and the static was already wrong in a quieter way — the class's scope genre is per-instance, so every test after the first was running against an account configured for a different scope.
